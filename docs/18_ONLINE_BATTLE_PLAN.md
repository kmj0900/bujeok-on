## 1. 왜 지금 하지 않나 (2026-11-25 결정)
- 현재 게임은 정적 사이트라 서버 코드가 없다. 온라인 대전은 **실시간 서버(WebSocket)**, 두 화면의 **동기화**, **지연·끊김 처리**가 새로 필요한 큰 작업이다.
- 두 기기로 계속 테스트해야 하고, 발표장 인터넷이 불안하면 온라인 대전이 가장 먼저 문제가 된다.
- 이미 잘 돌아가는 배포(`bujeok`)를 망가뜨릴 위험이 있어, 발표용은 그대로 두는 쪽을 택했다.
- 발표에서는 **확장 방향**으로 소개한다. 필요한 기능(온라인 대전·랭킹·로그인)이 없어서 서버 없이 정적으로 배포했다고 설명한다.

## 2. 목표와 범위
- 목표: **방 코드로 두 명이 각자 브라우저에서 1:1 대결**. 방을 만든 사람이 맵을 고르고, 규칙은 로컬 대결과 같다.
- 포함: 방 만들기·코드로 입장, 맵 선택, 카운트다운 동기, 대결, 결과, 연결 끊김 표시.
- 제외(처음엔 안 함): 로그인, 랭킹·전적 저장, 관전, 매칭(자동 상대 찾기), 3명 이상, 모바일 터치 조작.
- 한 판을 시연하려면 컴퓨터 두 대(또는 브라우저 두 개)가 필요하다.

## 3. 접근: 입력만 주고받는 동기화(락스텝)
서버는 상태를 계산하지 않고 **입력을 중계**만 한다. 양쪽 브라우저가 같은 규칙으로 같은 계산을 돌린다.

### 코드에서 확인한 것 (이 방식이 가능한 이유)
- 규칙 계산이 **고정 스텝 1/60초**(`game.js`의 `STEP`)로 돈다.
- 사람과 AI가 같은 **행동 형식** `{ move, placeBomb, struggle }`을 쓴다(`input.js`의 `getAction`, `player.js`의 `applyAction`).
- 난수가 **시드로 고정**돼 있다: 맵(상자·바위) `?seed`, 맵 위협 줄 선택 `map.seed + 29`(`hazard.js`), 아이템 추첨 `map.seed + 13`(`game.js`). `Math.random`은 AI 생성의 기본값에만 있고(`ai.js`), 온라인에서는 AI를 쓰지 않는다.
- 따라서 **같은 시드 + 같은 입력 순서 = 같은 결과**가 되도록 만들 수 있다. 다만 실제로 두 쪽이 완전히 같은 결과를 내는지는 아직 테스트하지 않았다(확인 안 함).

### 동작 흐름
1. 방 생성/입장: 서버가 방 코드를 만들고 두 사람을 묶는다. 방을 만든 사람은 1P(흑영), 들어온 사람은 2P(녹림)로 한다.
2. 시작: 서버가 `mapId`, `seed`, 시작 시각 기준 카운트다운을 **양쪽에 같은 값으로** 보낸다.
3. 매 스텝(또는 몇 스텝 묶음)마다 자기 입력을 서버로 보내고, 서버가 상대 입력을 전달한다. 양쪽은 **같은 틱 번호의 입력 두 개가 모두 도착해야 그 틱을 계산**한다.
4. 지연 완충: 입력 지연을 몇 틱(약 3~6틱, 50~100ms 안팎을 시작값으로 시험) 두어 서로의 입력이 늦게 와도 멈추지 않게 한다. 값은 두 기기로 실제 지연을 재고 정한다(확인 안 함).
5. 어긋남 감지: 일정 틱마다 상태 해시(플레이어 위치·체력, 부적 수)를 교환해 달라지면 경고한다.

### 로컬과 다르게 처리할 것
- **일시정지**: 온라인에서는 한쪽이 멈추면 상대가 기다려야 하므로 일시정지 대신 "상대를 기다리는 중" 표시, 탭을 숨기면(autoPause) 온라인에서는 정지하지 않고 입력이 비는 것으로 처리한다.
- **재대결**: 두 사람이 모두 누르면 새 시드로 시작.
- **연결 끊김**: 일정 시간 입력이 안 오면 끊김 표시 후 남은 사람 승리(또는 방 닫기).
- 화면 전용 효과(소리, 흔들림)가 상태에 영향을 주지 않는지 점검이 필요하다(확인 안 함).

## 4. 서버·배포 구조
- 서버: Node.js + WebSocket(예: `ws` 패키지). 방 목록·중계만 하고 게임 규칙은 모른다.
- 배포: **Render Web Service를 별도로 하나 더**(예: `bujeok-online`). 발표용 정적 사이트 `bujeok`은 건드리지 않는다.
- 클라이언트: 같은 저장소의 별도 브랜치(예: `online`) 또는 별도 저장소를 쓰고, 그 브랜치를 별도 Render 서비스로 배포한다(주소도 다르게).
- 주의(확인 필요): 무료 웹 서비스는 한동안 쓰지 않으면 잠들어 첫 접속이 느릴 수 있다고 알려져 있다. 발표 전에 Render 문서와 실제 동작을 확인한다. 이 한계는 정적 사이트에는 없다.
- 서버 주소는 클라이언트 코드에 환경별로 넣어야 한다(로컬 `ws://localhost:...`, 배포 `wss://...`).

## 5. 작업 단계 (순서대로, 각 단계는 자동 테스트부터)
| 단계 | 할 일 | 끝났다고 보는 기준 |
|---|---|---|
| M1 | 결정성 테스트: 같은 시드 + 같은 입력 기록을 두 번 돌려 최종 상태 해시가 같은지(Node) | 여러 맵·여러 시드에서 항상 같음. 다르면 어긋나는 원인부터 고친다 |
| M2 | 서버: 방 만들기·입장·퇴장 | 두 클라이언트가 같은 방에 묶임 |
| M3 | 입력 중계 + 틱 동기(락스텝) | 지연을 인위적으로 넣어도 두 쪽 해시가 같음 |
| M4 | 화면: 로비(방 만들기·코드 입력)·대기·카운트다운 동기·끊김 표시 | 두 브라우저에서 한 판 끝까지 |
| M5 | 지연·끊김·재대결·탭 전환 처리 | 와이파이가 흔들려도 게임이 깨지지 않음 |
| M6 | 별도 Render Web Service로 배포 + 서로 다른 두 기기 테스트 | 배포 URL에서 한 판 완주 |

## 6. 코드에서 건드릴 곳 / 건드리지 않을 곳
- 건드릴 곳: `input.js`(원격 입력 주입), `main.js`(온라인 장면·네트워크 연결), 새 파일(`net.js`, `server/`), `ui.js`(로비 화면).
- **건드리지 않을 곳**: 게임 규칙(`game`·`player`·`bomb`·`item`·`hazard`·`map`)과 AI. 규칙이 바뀌면 로컬 대결·자동 테스트 426개에 영향이 간다.

## 7. 위험과 대응
| 위험 | 대응 |
|---|---|
| 두 화면이 어긋남(동기화) | M1 결정성 테스트, 상태 해시 교환, 어긋나면 해당 판 종료 안내 |
| 지연 때문에 조작이 굼뜸 | 입력 지연 틱을 작게 시작해 실측 후 조정 |
| 발표장 인터넷 불안 | 발표는 로컬·AI 버전으로 하고 온라인은 영상·설명으로 대체 |
| 무료 서비스가 잠들어 첫 접속이 느림 | 발표 직전에 미리 접속해 깨워 두거나 온라인 시연을 하지 않음(확인 필요) |
| 작업 시간 부족 | 발표용 `bujeok`과 분리해서 만들고, 안정되지 않으면 합치지 않는다 |
| 기존 배포를 망가뜨림 | 별도 브랜치·별도 Render 서비스에서만 작업 |

## 8. 시작 조건과 판단
- 시작해도 되는 때: 발표 준비(URL 시연·녹화·발표 자료)가 끝났고, 시간이 남을 때.
- 합치는 조건: M1~M6가 통과하고, 두 기기에서 연속 여러 판이 어긋남 없이 끝날 때. 하나라도 불안하면 합치지 않고 "확장 방향 시연(영상)"으로만 쓴다.
- 시작 전에 사용자와 정할 것: 남은 기한, 컴퓨터 두 대로 테스트 가능한지, 브랜치로 할지 별도 저장소로 할지, 방 코드 방식으로 충분한지(자동 매칭은 제외).
